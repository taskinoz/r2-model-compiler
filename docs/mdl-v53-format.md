# Titanfall 2 MDL v53: layout notes

Facts used to write Titanfall 2 (v53) `.mdl` files. They were measured over the 602
`.mdl` files in `englishclient_mp_common.bsp.pak000_dir.vpk` (Titanfall 2 PC), and
checked by round trips and in game.

Struct layouts start from the public reverse-engineering notes in r-ex/rmdlconv
(`studio.h`, namespace `r2`) and r-ex/rsx (`studio_r2.h`). `tools/mdl53.py` is the
independent reader used for surveys and comparisons.

## Header and container

- `studiohdr_t` is 0x2CC bytes, with `id` = `IDST`, `version` = 53 and `length` = file size.
- One `.mdl` holds everything. `vtxOffset/Size`, `vvdOffset/Size`, `vvcOffset/Size` and
  `phyOffset/Size` point at embedded copies of the old separate files.
- Order at the end of the file: PHY, map collision (`collisionOffset`,
  `staticCollisionCount`), VTX, VVD, VVC. The blobs are not aligned. VVC (when present)
  or VVD ends the file.
- The VTX, VVD and PHY `checksum` fields equal the header `checksum`.
- Main body order: header, source-file block, bones, bone controllers, attachments,
  hitbox sets, bone-by-name table, animation descs, sequence descs, body parts, models
  and meshes, IK chains, pose parameters, IK autoplay locks, UI panels, include models,
  textures, cdtextures, skins, keyvalues, source bone transforms, linear bones,
  per-triangle AABB, string table, then the blobs above.
- `numcdtextures` is 1 in every model. `fadeDistance` is -1.0 in most models.
  `unkStringOffset` names `""` or `"Titan"`.
- Common header flags: 0x800011 (static prop, autogenerated hitbox, single bone),
  0x1800011 (adds vertex colour and a VVC block), 0x0, 0x1, 0x4.
- 0x800000 is set on every single-bone model, with or without physics. The exceptions
  have per-joint collision or no map-collision block.
- Without `$hbox` lines, retail sets the autogenerated-hitbox flag (0x1) but writes an
  empty set (384/387 such models).
- Header mass is 1.0 for models without physics, apart from a few with explicit
  values. `mstudiomodel_t.boundingradius` is always 0.
- Bone quaternions are `AngleQuaternion(rot)` unaligned (25,801/25,801 bones; 172 have
  w < 0).
- Sequence boxes (`CalcSequenceBoundingBoxes`): every posed vertex of every frame, plus
  each bone's hitbox bounds transformed as an AABB. Unlike Valve, the per-bone vertex
  bounds are not put through the AABB step. Rigid collision then expands sequence 0
  by its points in bind pose plus 0.25. The hull is sequence 0's box.
- Some attachments store an all-zero matrix.

## Bone followers

- `boneFollowerCount` / `boneFollowerOffset` (header 0x1D4 / 0x1D8): a list of int32
  bone indices, stored after the map-collision block and before the embedded VTX
  (outside the checksummed body).
- Used by animated single-player props (doors, cranes, platforms) whose physics
  follows their animation; no `mp_common` model has them.

## LODs

studiomdl keeps `$lod` script order. Switch distances are not sorted; retail has
models whose LOD 1 switches at 250 and LOD 2 at 40.

## Embedded VTX / VVD / VVC / PHY

- VTX header is always version 7, vertCacheSize 24, maxBonesPerStrip 160,
  maxBonesPerFace 9, maxBonesPerVert 3.
- Each mesh has 0 or 1 strip group. Each strip group has flag 0x02 (hardware skinned)
  and one strip, and the strip is a triangle list.
- VVD is version 4 with tangents. A VVC block is present when the vertex colour
  (0x1000000) or UV2 (0x2000000) flag is set.
- VVC layout: `IDCV`, version 1, checksum, LOD count, 8 per-LOD vertex counts, then
  offsets (from the VVC start) to the vertex colours (4 bytes each) and UV2 (2 floats
  each), both 16-byte aligned.
- VVD fixups: a fixup table exists exactly when the model has LODs and more than one
  mesh (121/121 such models; never for a single mesh, 75/75). Runs never continue
  across a mesh boundary, even when adjacent runs share a LOD.
- VVD/VVC `numLODVertexes[l]`: with a fixup table, the end offset of the last run that
  LOD `l` uses, not the number of vertices it uses (so LOD 1 often equals LOD 0).
  Without one, the true count. Slots past the LOD count repeat the last LOD's value.
  The VVC header holds the same counts as the VVD header.
- Vertex identity: retail keeps vertices that match in position, normal, UV and
  weights apart when their tangents differ (about 52,000 such pairs in LOD 0 alone).
  The split comes from the source mesh, so it cannot be rebuilt from geometry alone.
- Mesh order within a model follows the source's material order, not texture index.
  With skin families, the texture table lists each base texture followed by its
  replacements (169/169 multi-skin models).
- PHY header: `size` 16, `id` 0. Rigid models have one solid; ragdolls have several.
- Jointed solids are in the collision source's joint order, not bone order;
  `mstudiobone_t.physicsbone` is the solid index of the nearest ancestor (or self)
  with a solid.
- Jointed models can have several convex pieces per joint without a `"concave"` key in
  the PHY text (studiomdl's `$concaveperjoint`). `$concave` on a rigid model does
  write `"concave" "1"`.

## Per-triangle AABB block

- Present in every model. The header (`version`, bbmin, bbmax, unused ints) is 0x3C
  bytes.
- Animated and multi-bone models use version 0 with no nodes.
- Single-bone static props use version 2 with a node tree:
  - nodes are 20 bytes;
  - leaves are 0x70 bytes, with 12 triangles each;
  - vertices are 6 bytes, uint16 fractions of the bounds.
- A triangle's fourth field holds its surface property index from
  `surfaceproperties.txt` (for example 22 = metal, 16 = glass).
- The tree exists (version 2) for static props and for props whose keyvalues hold
  `prop_data { "allowstatic" "1" }` (21/21 such animated props); other models write
  version 0.
- `perTriAABBVertCount` is often the number of mesh vertices LOD 0 uses (vertices
  sharing a position are not merged), and on some models every VVD vertex. Others,
  such as pelican_case_ammobox (4,142 of 4,543), fit no LOD subset or position merge.
  Respawn likely built the list from its own source mesh.
- The tree splits large nodes at the median (the left half gets the smaller count).
  Smaller nodes split by another, apparently spatial, rule: leaves hold 0 to 12
  triangles, and a 12-triangle node can still split. That rule is not reproduced, so
  node and leaf counts differ from retail on about 105 models. Unused triangle slots
  are all zeros, so they can't be told apart from a triangle on vertex 0.

## RLE animation records

- Per-bone record layout:
  - float `posscale`, uint8 `bone`, uint8 `flags`, 2 pad bytes;
  - a 24-byte area: rotation (Quaternion64 when RAWROT 0x04, otherwise three int16
    value-pointer offsets), position at +16, scale at +22;
  - an int32 offset to the next record at +28, where 0 ends the chain.
- Animated value streams follow the 32-byte record.
- Animations with at least 120 frames use `sectionframes` 30, with
  `(numframes - 1) / sectionframes + 2` section offsets.
- An empty animation is a single record with bone 255 and flags 0.
- `posscale` is per bone for the whole animation (identical in every RLE section).
- One-frame chains (the trailing section and single-frame animations) are always raw.
  Retail never uses flags 0x0c.
- Retail never writes a non-raw record whose three position value pointers are all
  null; partially null pointers are common.

## Frame movement (STUDIO_FRAMEMOVEMENT 0x40000)

- `mstudioframemovement_t` is float scale[4] plus short offset[4] (offsets from the
  struct), followed by RLE streams for x, y, z and yaw (degrees). Scale floors are
  128/32767 (position) and 180/32767 (yaw).
- Yaw is wrapped to [-180, 180].
- The yaw follows the heading of the root bone's local Z axis relative to frame 0,
  within about 0.003-0.04 degrees. The root bone keeps pitch, roll and a small
  residual.
- Delta animations may carry an all-zero track (flags 0x40004).

## Bone scale animation

- Scale lives at record +22: a Vector48 when RAWSCALE (0x08) is set, otherwise three
  value pointers. Decoded scale = bone scale + value * bone scalescale (delta
  animations add no bone scale). Neutral raw scale is (1, 1, 1).
- Bone `scalescale` is always 1/2048 and bone `qAlignment` is always zero in retail.
- Animation flag 0x20000 (STUDIO_HAS_SCALE) is set on exactly the animations whose scale
  differs from 1, and on the sequences that use them.

## Animation and sequence flags

- Retail animation descs use only 0x1, 0x2, 0x4, 0x20, 0x20000 and 0x40000 (never
  0x8000 noforceloop). Sequence flags never carry 0x40000 or 0x8000.
- Delta animations (0x4) must keep the flag. Autoplay delta layers otherwise overwrite
  the root bone. All-zero deltas from `noanimation` are 0x24.
- Sequences do not inherit their named animations' flags. Blend pose keys need not be
  evenly spaced.

## IK rules

- `mstudioikrule_t` is 0x8C bytes: Valve's layout plus `endHeight` at +0x68 and 8
  unused ints.
- Rules sit between an animation's data and its frame-movement block.
- Each compressed error block (`float scale[6]; short offset[6]` plus 6 RLE streams)
  follows its rule and covers the whole animation, even a sectioned one.
- Rule types seen: release (mostly studiomdl's automatic release), footstep, unlatch,
  attachment.
  - Footstep rules have height 50, radius 15, floor 0 and endHeight -100.
  - Release rules keep a zeroed q.
- `index` is the rule's position for the animations a sequence uses, and 0 otherwise. A
  sequence's `numikrules` is the maximum over its blends.
- Footstep targets follow the full frame-movement transform:
  target(t) = inv(FM(t)) * FM(contact) * footfall. Frames past the end of a wrapped
  range use frame t - nf.
- studiomdl range quirks appear in retail:
  - A rule with start `.` overwrites the previous same-chain rule's end, after that
    rule was wrapped.
  - A rule with end `.` overwrites the next rule's start.
  - The original value can be recovered from the error-stream frame count.
  - The rewritten range can stay in order, so only the stream length shows it.
    `iStart` holds the stored (rewritten) start. A footstep's error is zero in x/y at
    its contact frame, which shows whether the stream begins at an earlier original
    start or runs to a later original end.

## Sequence weight lists

A sequence's weight list is not the weight its animations were encoded with. For
example, a sequence may weight the root 0 although its animation stores root records.

## Procedural bones

- Jiggle bones are type 5. Without the base-spring flag they store base mass 0,
  stiffness 100 and limits of ±100 (studiomdl defaults).
- Valve's layouts for the other types:
  - axis interpolation (1): 176 bytes;
  - quaternion interpolation (2): 12 bytes plus 48 per trigger;
  - aim at bone (3) / aim at attachment (4): 44 bytes.
- An aim target name is resolved against attachments before bones.
- Titanfall 2 evaluates procedural bones on the client. Server-side
  `GetAttachmentOrigin` ignores them.
- Only "used by" flags may propagate to parent bones. Propagating
  BONE_ALWAYS_PROCEDURAL (0x4) makes every ancestor of a jiggle bone procedural, and
  their animation is then dropped.

## UI panels (RUI meshes)

- **Header table:** at `uiPanelOffset` (0x12C), with the count at 0x128. Each entry is
  `{uint32 hash; int meshOffset}`, the offset relative to that entry. With no include
  models, `includemodelindex` equals `uiPanelOffset`.
- **Mesh header:** each mesh is 16-byte aligned. It starts with a 32-byte header:
  parentCount, vertexCount, faceCount, parentOffset, vertexOffset, indiceOffset,
  boundsOffset, and a uint32 CCW bitfield. The panel name follows at +32.
- **Offsets:**
  - vertexOffset = align16(32 + strlen + 1 + 2 * parents + 6 * faces)
  - indiceOffset = vertexOffset - 6 * faces
  - parentOffset = indiceOffset - 2 * parents
  - boundsOffset = vertexOffset + 16 * vertices
- **Mesh data:**
  - Parents are int16 bone indices (one or two).
  - Faces are three int16 corners of a parallelogram; the fourth is a + c - b.
  - Vertices are `{int parentSlot; Vector pos}`.
  - Bounds are 8 floats per face (x[4], y[4]).
  - At most 256 vertices and 64 faces; only the first 32 faces can be CCW.
- **Hash:** a weapon script's `UiDataN` block names a panel with `"mesh"`, and the client
  finds the panel by this hash of that name (found by disassembling `client.dll`):
  MurmurHash3 x86_32 with seed 0, every byte ANDed with 0xDF (so case is ignored), and
  the length including the terminating nul. It reproduces all 163 retail panel hashes.
  A zero or wrong hash hides the panel in game.

## Map-collision block

- **Header:** 5 int32 per piece: faces, faces + bevels, edges, vertices, and a data
  offset relative to the entry.
- **Data:**
  - planes, 16 bytes each (faces, then bevels);
  - edges, 28 bytes each (origin, delta, 2 side indices, 2 vertex indices);
  - vertices, 12 bytes each.
- A bevel plane is written for an edge only when dot(n0, n1) < 0.26.
- Edges index their side planes and vertices with single bytes. Retail pieces reach
  82 faces, 99 planes, 123 edges and 64 vertices (single-player rocks).
- Some retail models with ordinary PHY data have no block at all: `collisionOffset` is
  0, the count is 0 or -1, and bones store (0, 0). They appear to come from tools that
  predate the block.
- **Rigid models:** `staticCollisionCount` is the piece count, and every bone's
  collision index is 0xFFFF.
- **Jointed models:** the header count is 0, and each bone that owns a solid stores its
  collision index and count (bone +0xD4 and +0xD6).
- **Models without PHY:** every bone stores (0, 0).
- **Faces are source polygons.** Retail brush faces are the collision mesh's polygons
  (Maya quads and n-gons): 33,223 triangles, 39,523 quads and 2,404 larger polygons.
  Exactly coplanar neighbours stay apart; slightly bent quads (up to 0.01 units off
  plane) stay one face. A planarity merge cannot reproduce this; keeping DMX polygons
  can.
- **Surface points:** a piece keeps source points lying on its surface without being
  corners (cylinder-cap centres, edge midpoints). The PHY triangulates around them, and
  the block lists them as vertices even when no face edge uses them (46 retail pieces).
  A fresh convex hull drops them.
- **Collinear corners and T-junctions:** a face loop can include a point along a
  neighbour's edge; both faces then split that edge. A few retail faces touch
  themselves (an outline passing a vertex twice), so two edges join the same pair of
  faces.
